### Запрос

Разработать `InputPassword` на основе `InputText`, затем уточнить поведение text-field family и обновить память проекта.

### Итог

Добавлен `src/components/input-password` как sibling-компонент к `InputText`: поле по умолчанию скрывает символы, показывает visibility-toggle справа от clear-кнопки, восстанавливает позицию caret при переключении `password/text` и рендерит toggle только при непустом значении. По ходу UX-итераций из `InputText` и `InputPassword` убран placeholder, helper text ограничен только error-состояниями, а затем то же правило применено к `InputPhone`. Для Storybook у `InputPassword` временно отключён `autodocs`, потому что docs-страница нового компонента зависала на спиннере, хотя обычные stories продолжали собираться.

### Изменённые файлы

- `src/components/input-password/InputPassword.scss`
- `src/components/input-password/InputPassword.stories.tsx`
- `src/components/input-text/InputText.tsx`
- `src/components/input-text/InputText.stories.tsx`
- `src/components/input-phone/InputPhone.tsx`
- `memory/knowledge/concepts/input-text-floating-label-control.md`
- `memory/logs/2026-04-22.md`

### Решения

- `InputPassword` фиксируется как часть text-field family поверх паттерна `InputText`, а не как отдельный произвольный input со своей state-моделью.
- Для пустого text field не использовать placeholder: визуальную роль первичного текста полностью несёт floating label.
- Helper text в family text inputs показывается только в error-состояниях, чтобы не ломать вертикальный ритм и Figma state matrix.
- При переключении видимости пароля нужно сохранять и восстанавливать `selectionStart/selectionEnd`, иначе caret сбрасывается в начало.
- Если новый form control зависает только в Storybook Docs, можно временно убрать `autodocs` и продолжить работу через обычные stories, а root cause докапывать отдельно.

### Риски

- Root cause зависания `InputPassword` Docs пока не локализован окончательно; зафиксирован только безопасный workaround через отключение `autodocs`.
- Workspace по-прежнему не является git repository, поэтому `git status` и `git diff` недоступны из этой папки.

### Follow-ups

- При следующей работе с text-field family сверить `InputText`, `InputPassword`, `InputPhone` и modal text-input variant, чтобы не разъехались правила helper/label/actions.

### Решения

- `InputMiddleName` закрепляется как композиция над существующими `InputText` и `Switch`, а не как новая самостоятельная state-машина text field.
- `InputCode` закрепляется как sibling text-field family поверх стилистики `InputText`, но с отдельной логикой фильтрации цифр, маски и отключения browser suggestions.

- `autoComplete=\"off\"` и родственные атрибуты обычно убирают браузерные подсказки, но отдельные password managers или browser extensions всё равно могут пытаться показывать собственные overlays.
- `InputCode` пока реализован как одно поле с маской, а не как OTP-grid из отдельных ячеек; если продукту позже понадобится сценарий одноразового кода из SMS, может понадобиться сверка с `code-input-item`.

### Запрос

Разработать `DatePicker` по Figma, разобраться с зависанием story в Storybook и зафиксировать правила валидации даты рождения.

### Итог

Добавлен `src/components/date-picker` как новый sibling-компонент в text-field family. В desktop-режиме он рендерит поле с маской `дд.мм.гггг` и flyout на базе library `Calendar`, а на mobile/tablet использует нативный `input[type=\"date\"]`. По ходу отладки выявилось, что встроенный браузер Storybook продолжал показывать spinner: для снижения риска были упрощены stories и добавлен fallback `matchMedia.addListener/removeListener` для IAB/webview-совместимости. Затем в `DatePicker` и `Calendar` зафиксированы продуктовые ограничения для даты рождения: только реальные даты, день `01-31`, месяц `01-12`, возраст на момент проверки от `18` до `100` лет, и тот же диапазон применяется к нативному пикеру и flyout-календарю через `minDate/maxDate`. В финале у компонента закреплён пустой default-state без даты и label `Дата рождения`.

### Изменённые файлы

- `src/components/date-picker/DatePicker.tsx`
- `src/components/date-picker/DatePicker.scss`
- `src/components/date-picker/DatePicker.stories.tsx`
- `src/components/calendar/Calendar.tsx`
- `src/components/calendar/Calendar.scss`
- `memory/knowledge/concepts/calendar-date-picker.md`
- `memory/logs/2026-04-22.md`

### Решения

- `DatePicker` закрепляется как birth-date control поверх существующего `Calendar`, а не как thin wrapper над сторонней date-библиотекой.
- Для desktop/mobile divergence используется responsive runtime-switch, но компонент обязан иметь fallback для legacy `MediaQueryList` API, чтобы не ломаться в IAB.
- Валидность даты рождения нужно проверять не только на финальном значении, но и на уровне ввода по сегментам и на уровне calendar/native picker selection.
- Базовое состояние `DatePicker` — пустое поле; предзаполненная demo-date не должна masquerade-ить production-default.

### Риски

- Несмотря на добавленный fallback, root cause spinner-состояния во встроенном Storybook-браузере может иметь дополнительный вклад от самого IAB; подтверждён только один безопасный mitigation path.
- Текущий `DatePicker` заточен под дату рождения; если позже появятся general-purpose date inputs без возрастных ограничений, вероятно, понадобится отделить общую базу от birth-date specialization.

### Follow-ups

- При следующем заходе в Storybook через обычный desktop-браузер и через IAB сравнить поведение `DatePicker`, чтобы подтвердить, что spinner больше не связан с responsive/media-query веткой.

- Для надежного mobile-preview внутри Storybook и других ограниченных контейнеров auth template должен поддерживать явный `device`-режим, а не только media-query адаптацию.
- В auth-сценариях ссылочные элементы должны использовать token-driven состояния `default / hover / focus`.
- Text-field family в обычных состояниях должна оставаться с прозрачным surface, без собственного фонового слоя поля.

### Риски

- `AuthenticationFirstScreen` пока покрывает только первый auth-экран; при добавлении следующих экранов нужно будет следить, чтобы локальные layout-исключения не размыли общие правила auth-template слоя.
- Прозрачный surface уже закреплён для нескольких text-field компонентов; если в проекте есть старые stories или сценарии, рассчитанные на заливку поля, их может понадобиться сверить отдельно.

### Follow-ups

- При добавлении следующих auth templates проверить, что они reuse-ят `Header`, соблюдают `fill`-layout и не вводят локальные ссылки/поля с обходом token-driven правил.
