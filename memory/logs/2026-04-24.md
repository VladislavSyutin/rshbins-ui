### Запрос

Обновить память проекта после серии правок auth prototype по регистрации КК, восстановлению логина и captcha/timeout ветке на первом экране

### Итог

Зафиксированы новые сценарии в `AuthenticationPrototype`: registration flow с loading submit-кнопки на `AuthenticationRegistrationINN`, visible email/phone confirmation и переходом на создание логина и пароля; login recovery flow с visible confirmation и переходом на создание только логина; special-case ветка для телефона `79999999992` с loading кнопки первого экрана, modal `Captcha`, последующей loading кнопки captcha и `Timeout` modal с реальным 30-минутным countdown для значения `timeout`.

### Изменённые файлы

- src/components/prototypes/authentication/AuthenticationPrototype.tsx
- src/components/templates/authentication/authentication-registration/AuthenticationRegistration.tsx
- src/dialogs/modals/timeout/Timeout.tsx

### Решения

- Для регистрации КК переход `AuthenticationRegistrationINN -> confirmation` не использует fullscreen `LoaderBrand`: 3 секунды держатся на loading state кнопки `Зарегистрироваться`.
- Для registration confirmation переход после OTP не должен включать fullscreen loading поверх `InputCodeItem`; сначала должна завершиться встроенная 3-секундная loading-анимация OTP-контрола, потом открывается экран создания логина и пароля.
- Для восстановления логина переход `AuthenticationRestoringAccess -> visible confirmation` держится на loading state submit-кнопки, а не на fullscreen loader.
- Для номера `79999999992` первый экран сначала показывает loading кнопки входа 3 секунды, затем открывает `Captcha`; для ввода `timeout` `Captcha` тоже сначала показывает 3-секундный loading state кнопки, и только затем открывается `Timeout`.
- `Timeout` больше не хранит статическое время в тексте: modal сам считает оставшееся время от 30 минут вниз с шагом в 1 секунду.

### Риски

- Demo-ветки всё ещё завязаны на конкретные тестовые значения телефонов и captcha input; при переходе к production-логике эти условия нужно вынести в API-driven статусы.

### Follow-ups

- При следующем обновлении knowledge слоя стоит синхронизировать заметку про `dialog-templates-layer`, если `Timeout` countdown и `Captcha` loading станут устойчивыми reusable паттернами вне auth prototype.

### Запрос

Обновить память проекта после мобильных правок auth prototype и `InputBirthDate`

### Итог

В памяти зафиксированы мобильные уточнения для auth-flow и form controls: `AuthenticationPrototype` теперь прижат к верхнему краю mobile viewport с нижним отступом `32px`; `AuthenticationRestoringAccess` использует укороченные mobile labels в segmented control; строка `InputBirthDate + Gender` больше не растягивает `Gender` при ошибке даты; mobile native `InputBirthDate` показывает выбранную дату, корректно обрабатывает reset из системного календаря и для даты вне диапазона 18-100 лет возвращает отдельную ошибку вместо текста об обязательном заполнении.

### Изменённые файлы

- src/components/prototypes/authentication/AuthenticationPrototype.scss
- src/components/templates/authentication/authentication-registration-data/AuthenticationRegistrationData.scss
- src/components/input-birth-date/InputBirthDate.tsx
- src/components/templates/authentication/authentication-restoring-access/AuthenticationRestoringAccess.tsx

### Решения

- Mobile auth layout выравнивается по `0px` сверху, а нижний воздух задаётся контейнером прототипа, а не внутренними шаблонами.
- Короткие mobile labels в восстановлении доступа должны включаться и в `device="auto"` при viewport до `743px`, а не только при явном `device="mobile"`.
- Для mobile native `InputBirthDate` выбранное значение должно отображаться отдельным видимым слоем, потому что скрытый нативный `input[type=date]` не даёт стабильной визуализации внутри token-driven поля.
- Для native picker reset/clear нужно слушать и через `change`, и через `input`, иначе системная кнопка сброса на мобильных браузерах может не обновить контрол.
- Ошибка возраста вне диапазона должна различаться с пустым полем: пустое значение остаётся `Обязательно для заполнения.`, а дата вне 18-100 лет показывает отдельный текст диапазона.

### Риски

- Поведение native date picker остаётся зависимым от браузера и ОС, поэтому любые будущие изменения в `InputBirthDate` нужно перепроверять именно на мобильных устройствах, а не только в desktop Storybook.

### Follow-ups

- Если появятся ещё мобильные form controls с нативными input overlays, стоит вынести для них общее правило в отдельную knowledge note про mobile-native fields.
