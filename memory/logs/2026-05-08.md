### Запрос

Глубокий аудит совместимости legacy-слоя со стеком ФОС по присланным образцам кода и документу core-сервиса

### Итог

Проведён детальный сравнительный анализ legacy/ против реального кода ФОС (Form, Input, Panel, Field из zip-архива) и описания стека ФОС (React 17 / Webpack 3 / MobX 4 / Jest + Enzyme / react-text-mask). Выявлено 11 расхождений, каждое обсуждено с владельцем. Итог: ни одного реального блокера — все критичные вопросы сняты или приняты. Токены уже совместимы (ФОС переходит на токены с этого проекта). Form/Field/Panel/Fieldset не нужны (ФОС использует только то, что есть в sandbox). data-id никогда не существовал в legacy-слое — нет следов в git и memory, обсуждался устно. Функциональные компоненты/хуки — ФОС примет как есть. PropTypes — не критично, devs работают с кодом напрямую. Input-архитектура (13 компонентов vs 1 монолитный) — оставляем. react-text-mask — не нужен, legacy components self-contained. Unit-тесты — Storybook достаточен, ФОС напишет свои при интеграции. BEM-нейминг — оставляем. Export-синтаксис — текущий стандартнее, оставляем. Readme-формат — оставляем, Stories замещают примеры.

### Изменённые файлы

- Файлы не указаны.

### Решения

- Токены: legacy-компоненты используют те же CSS custom properties что и modern — это правильно, ФОС переходит на токены начиная с этого проекта аутентификации
- Form/Field/Panel/Fieldset/Select: не нужны в legacy-слое для этого проекта — ФОС использует только компоненты из текущего sandbox
- data-id/dataId: этого prop никогда не было в legacy-слое (не найдено в git-истории и memory). Если ФОС-разработчики запросят — тогда добавлять
- Функциональные компоненты с hooks: оставляем. Hooks работают в React 17 (начиная с 16.8). ФОС-команда примет функциональный стиль, переписывать 34 компонента не нужно
- PropTypes: не добавляем. ФОС-разработчики смогут работать с кодом напрямую. TypeScript .d.ts файлы есть, Stories есть, Readme есть — документации достаточно
- Input-архитектура: оставляем 13 отдельных специализированных input-компонентов вместо одного монолитного с mask-prop. ФОС берёт готовый InputPhone — маска уже внутри
- react-text-mask: не интегрируем. Legacy inputs self-contained, каждый со своей логикой форматирования. Masking работает визуально в Storybook
- Unit-тесты (.test.jsx для Jest+Enzyme): не добавляем. Storybook — поверхность визуальной проверки. ФОС напишет свои тесты в своём окружении при интеграции
- CSS BEM-нейминг с rshb-legacy-* префиксом: оставляем. Не конфликтует с ФОС-кодом, изолирует legacy от modern
- Export-синтаксис: export { default } from './X.jsx' — стандартный ES2015, оставляем. ФОС-синтаксис export default from './X' — stage-1 proposal, требует babel-плагин. Текущий вариант совместимее
- Readme-формат: оставляем. Stories в Storybook = интерактивная документация. Readme с коротким примером достаточен

### Риски

- Если ФОС-разработчики привыкли к class components и не знакомы с hooks — могут возникнуть вопросы при изменении компонентов. Смягчение: можно добавить краткую заметку в README legacy/ о том, что компоненты написаны на функциональном React
- data-id отсутствует в legacy-компонентах. Если ФОС используют data-id для QA-автоматизации или E2E-тестов, им придётся добавить атрибуты самим при интеграции
- Storybook не гарантирует безболезненную интеграцию в Webpack 3 / React 17 среду без пилотной проверки на стороне ФОС

### Follow-ups

- Если ФОС-разработчики сообщат о проблемах при интеграции — фиксировать конкретные жалобы и решать адресно, не переписывать всё заранее
- Если ФОС запросят data-id поддержку — добавить prop dataId?: string в компоненты и передавать как data-id на root element
- Если ФОС запросят PropTypes — добавить как отдельный batch, приоритет по компонентам которые они используют чаще всего

### Запрос

Добавить автоматическую транслитерацию раскладки клавиатуры в полях ввода с ограничением на язык

### Итог

Создана утилита транслитерации (src/components/transliterate.ts, legacy/components/transliterate.js) с маппингом QWERTY↔ЙЦУКЕН. Все sanitize-функции в InputName, InputSurname, InputMiddleName (EN→RU), InputLogin, InputEmail, InputPassword (RU→EN) обновлены: перед сбросом символа пробуем транслитерировать его в нужную раскладку. Дополнительно: смещённый цифровой ряд — « → @, № → # для Latin-полей. Оба слоя (modern src/ и legacy/) поправлены.

### Изменённые файлы

- src/components/transliterate.ts
- legacy/components/transliterate.js
- src/components/input-name/InputName.tsx
- src/components/input-surname/InputSurname.tsx
- src/components/input-middle-name/InputMiddleName.tsx
- src/components/input-login/InputLogin.tsx
- src/components/input-email/InputEmail.tsx
- src/components/input-password/InputPassword.tsx
- legacy/components/input-name/InputName.jsx
- legacy/components/input-surname/InputSurname.jsx
- legacy/components/input-middle-name/InputMiddleName.jsx
- legacy/components/input-login/InputLogin.jsx
- legacy/components/input-email/InputEmail.jsx
- legacy/components/input-password/InputPassword.jsx

### Решения

- Транслитерация работает на уровне символа внутри sanitize-функции: если символ уже проходит паттерн — берём как есть; иначе — транслитерируем; иначе — отбрасываем. Это не меняет логику валидации.
- Смещённый цифровой ряд вынесен в отдельные словари SHIFTED_NUMBER_ROW_*, а не в основной маппинг, чтобы избежать коллизий (один символ может появляться с разных физических клавиш в разных раскладках).

### Риски

- Символы типа / и | могут вести себя нестандартно в некоторых RU-раскладках macOS, но они не являются обязательными в полях и сейчас не обрабатываются.

- Следующие шаги не зафиксированы.
